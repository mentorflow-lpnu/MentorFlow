## Наслідки вибору Firestore

- **Запити простіші, ніж SQL:** без JOIN, а складні фільтри потребують індексів. Тому дані зберігаються одразу у зручному для читання вигляді.
- **Grafana не читає Firestore з коробки.** Потрібен плагін Firestore data source, його треба перевірити на старті. Запасний варіант: n8n → Google Таблиця → Looker Studio.
- **n8n і Grafana однаково треба десь запускати** (Docker Compose).

## Обговорення: TL;DR змін PR від LLM

Під карткою PR може бути автоматичний короткий опис змін від LLM. У першій версії його немає, але питання лишається відкритим.

**Як це могло б працювати:**
1. Бот бере diff PR, відкидає lock-файли й збірки, обрізає до ~12 тис. символів.
2. Модель повертає 1–2 речення про суть змін і до трьох пунктів «на що звернути увагу».
3. Підходить будь-яка модель з OpenAI-сумісним API, зокрема локальна.

**Що обговорити:**
1. Чи читатимуть рев'юери TL;DR, чи досить назви, опису й кількості рядків?
2. Diff — це код команди, який іде стороннім сервісам. Чи це допустимо?
3. Вартість і ліміти безкоштовних тарифів.
4. Якість на великих PR, де частину diff обрізано.
5. Чи хочемо згодом автоматичні коментарі-рев'ю своїми моделями?

| Варіант | Плюси | Мінуси |
|---|---|---|
| без LLM | нуль вартості й ризиків | без опису змін |
| безкоштовний хмарний API (Groq, OpenRouter free) | безкоштовно, швидко | ліміти; код іде стороннім |
| платний API (OpenAI, Anthropic) | найкраща якість | гроші; код іде стороннім |
| локальна модель (LM Studio, Ollama) | код нікуди не йде | потрібен комп'ютер, що працює весь час; слабша якість |
| список змінених файлів замість LLM | просто, без ризиків | це не опис суті |
